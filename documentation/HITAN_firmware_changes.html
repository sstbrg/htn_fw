§1  110 kbps data-rate migration

Switches the radio from 850 kbps to 110 kbps for greater RX sensitivity / range. Apply identically on Tag and Anchor — UM Table 21: the receiver must use the same data-rate/SFD config as the transmitter, or ranging stops entirely.

Preamble length: go to 2048, not 1024. UM Table 57 (Recommended preamble lengths): 110 kbps → 2048 or 4096 (850 kbps → 256/512/1024; 1024 is the top of the 850k range, below the 110k floor). For a max-range 110k system use PLEN_2048, which per UM Table 6 requires PAC64. The firmware author already anticipated this — the commented block at anc/inc/dw1000.h:133–144 is exactly DWT_PLEN_2048 / DWT_PAC64 / DWT_BR_110K. A longer preamble adds airtime (drives the timeout values up, below) and slightly lengthens the round-trip — still far under the ~67 ms 32-bit wraparound limit (1B), so it is safe; just keep the reply delays tight.

§2  TX-1 errata — force TX clock before delayed transmit

2A  important  Enable TX clock before each delayed dwt_starttx — tag/src/dw1000.cpp:241 & anc/src/dw1000.cpp:411

/* current: delayed TX issued without the errata workaround */
ret = dwt_starttx(DWT_START_TX_DELAYED);

/* → force TX clock on first (PMSC_CTRL0 bits 5,4 = 1,0) */
dwt_write8bitoffsetreg(PMSC_ID, PMSC_CTRL0_OFFSET,
    dwt_read8bitoffsetreg(PMSC_ID, PMSC_CTRL0_OFFSET) | 0x20);  // TXCLKS = 125MHz
ret = dwt_starttx(DWT_START_TX_DELAYED);

Errata §3.1.3 (verbatim): "If the TX clock is enabled (PMSC_CTRL0 bits 5,4 set to 1,0 - force TX clock on) before the delayed TX command is issued then the problem does not happen." The stock dwt_starttx() does not do this — it is the wrapper's job and is currently absent. A silently-failed delayed TX means the responder never replies → lost exchange; costs frames at the range edge where you can least afford them. Affects both SS-TWR response transmissions.

§3  Rev-D receive deafness — enable GPIO clocks for the external LNA

Leading suspected root cause of the Rev-D long-range failure. dwt_setlnapamode(...|DWT_LNA_ENABLE) configures GPIO6 = EXTRXE to switch in the external RX LNA — but the firmware never calls dwt_enablegpioclocks(), and dwt_setleds() enables only the de-bounce clock (GPDCE), not the GPIO clock (GPCE/GPRN). UM §7.2.39: "the GPIO clocks need to be turned on, before enabling or disabling the GPIO mode or value … by setting GPCE and GPRN in PMSC_CTRL0." If the GPIO write doesn't take effect, EXTRXE never asserts, the Rev-D LNA is bypassed, and the receiver is deaf — exactly matching RX-only, board-specific (Skylab's integrated front-end doesn't depend on EXTRXE).

3A  blocker  Add dwt_enablegpioclocks() after dwt_setlnapamode() — tag/src/dw1000.cpp:113 & anc/src/dw1000.cpp:93

dwt_setlnapamode(DWT_PA_ENABLE | DWT_LNA_ENABLE);
dwt_enablegpioclocks();  // REQUIRED: sets PMSC_CTRL0 GPCE|GPRN so EXTRXE (GPIO6) actually drives the LNA

One line, both files. APS004 §2: GPIO6/EXTRXE "goes high when the DW1000 is in receive mode" and (reference schematic) drives the RX-path RF switch into the LNA. This fix is curative only if Rev-D's LNA is gated by EXTRXE — confirm with §6 before concluding it is firmware-fixable vs a passive RX-front-end (matching/NF) hardware deficit.

Honest caveat: that an un-clocked GPIO_MODE write silently fails is documented in the UM but not independently re-confirmed by us; treat §3 as a high-probability hypothesis to verify on the bench (§6), not a settled fact. TX works at 2 km because the TX external-PA control (EXTPA/EXTTXE) is driven by the digital TX sequencer path, which is why the failure is RX-only.

§4  Long-range link-budget hardening

4A  important  TX power temperature compensation — dwConfig, anc/src/dw1000.cpp:80–106 & tag/src/dw1000.cpp:102–136

TX power is set once at boot via dwt_configuretxrf(); dwt_readtempvbat() / dwt_calcpowertempadj() are never called. APS023 Pt 1 §8.2: channel-2 TX power falls ~0.035 dB/°C → a −10 °C→+30 °C outdoor swing ≈ 1.4 dB of lost EIRP, straight off the long-range budget. Fix: periodically (post-wake / on temperature delta) read chip temperature and re-apply temperature-compensated power before TX.

4B  important  Per-device antenna-delay calibration — anc/inc/dw1000.h:149–150 ; tag/Inc/dw1000.h:92–93

Antenna delays are hardcoded (anc 16550/16500; tag 16500/16500). APS014: uncalibrated antenna delay ≈ 30 cm 3σ error, drifting 2.15 mm/°C. This is a constant offset (doesn't grow with range, won't stop you reaching distance) but it is your absolute-accuracy floor — calibrate per unit if sub-30 cm accuracy matters.

§7  LDE algorithm tuning — weak-signal first-path detection

Do §3 (RX path) first. LDE operates on signal that already reached the receiver. If Rev-D's LNA isn't switched in, no LDE value recovers a signal that is below the noise floor. Tune LDE after the receiver is actually hearing — to squeeze the last few dB of weak-signal margin, not as the cure for the 400 m failure. Hence experiment, not blocker.

What the firmware runs today (verified): dwt_configure() calls the stock _dwt_configlde(), which writes LDE_CFG1 = LDE_PARAM1 = PEAK_MULTPLIER(0x60) | N_STD_FACTOR(13) = 0x6D (PMULT=3, NTM=13) and LDE_CFG2 = 0x0607 for 64 MHz PRF. The #ifdef NEW_NTM block at anc/src/dw1000.cpp:110–114 is compiled out — and even if enabled it re-writes the same 0x6D, so it is a no-op-in-waiting, not the NLOS tuning its comment implies.

7A  experiment  Lower the LDE first-path threshold (NTM + PMULT) — write after dwt_configure(), e.g. anc/src/dw1000.cpp:110 / tag/src/dw1000.cpp ~118

LDE_CFG1 (reg 0x2E:0806) is one byte = PMULT (bits 7:5) + NTM (bits 4:0). Your current 0x6D is tuned for close-up line-of-sight accuracy — the opposite of what a weak long-range first path needs.

LDE_CFG1PMULTNTMMeaning (UM §7.2.47.2, verbatim guidance)
0x6D (now)313"used … to give more accuracy in close-up LOS conditions." Highest threshold — most likely to miss a weak/attenuated first path.
0x6C312Decawave default — "reasonable compromise … between falsely triggering on noise peaks and missing real attenuated first paths."
0x07 (NLOS)07NTM: "Where NLOS performance is more important … the default NTM value of 0x07 … would be a better choice."   PMULT: "For NLOS operations these bits should be set to 0."
 
/* after dwt_configure() — it calls _dwt_configlde() and would overwrite an earlier write */
/* sweep this value on the bench; lower = detects weaker first paths, but risks noise lock */
dwt_write8bitoffsetreg(LDE_IF_ID, LDE_CFG1_OFFSET, 0x07);  // PMULT=0, NTM=7 (NLOS / long-range)

Sweep, don't slam: 0x6D (now) → 0x6C (default) → 0x07 (NLOS). Measure first-path detection rate and range scatter at 400 m / long range at each. Too low a threshold makes LDE lock onto noise → false detects and garbage ranges → more effective loss. APS006 Part 2/3 is the tuning reference.

Placement: must be written after dwt_configure() (which sets the LOS default 0x6D), on the anchor that is the existing NEW_NTM location. Apply identically on Tag and Anchor.  Live-tunable from rf_analyzer ✓ — LDE_CFG1 is at reg 0x2E, sub-offset 0x0806. The firmware WRITE opcode (14) carries a 16-bit reg_offset (same struct as the READ opcode, whose ACC_MEM reads already use offsets >0xFF in production), so 0x0806 is reachable. commands.UWB_write8bit_raw now sends the offset as little-endian [lo,hi]; the analyzer Configuration tab has a "Live LDE tuning" control to sweep 0x6D/0x6C/0x07 in the field without re-flashing. (Earlier note said this needed a flash — corrected: only LDE_REPC math is driver-side; the byte itself is pokeable live, but resets to 0x6D on any dwConfig() re-run.)

Related, NOT a tuning knob: LDE_REPC (reg 0x2E:2804) must be divided by 8 at 110 kbps — dwt_configure() does this automatically (reg16 >>= 3 for DWT_BR_110K). Leave it alone; do not hand-write it.

§8  Multi-station coexistence — UWB backoff (two anchor systems, one tag)

Line numbers in this section reference the anchor source in firmware_code_for_reference/anchor-tag-bootload-backup-23-9-2026.zip (Anchor/Core/…, firmware sC3.0.67), which is the build that carries opcode 19 (BACKOFF_CTRL). Added 2026-10-13.

Goal. Two stations with different PC_ID (e.g. Mob + Fly) range the same tag. The tag answers whichever anchor polls it (tag/…/dw1000.cpp:253 checks only des == SELF_ID, no pc_id filter), so the only shared resource is the air. The anchor already implements a passive listen-before-talk: between UART commands it sits in dwScanMode() (main.cpp:408, gated by BackOFF_CTRL); any frame whose pc_id (src>>2 for anchor frames, des>>2 for tag frames) is foreign arms backoff_timer = now + random()%200 + 10 (dw1000.cpp:201, i.e. 10–209 ms); a SEARCH_TWR that arrives while it is armed skips dwRange() and answers with errors.bit4 = UWB_Backoff (main.cpp:252, uart_communication.c:176). The PC side will treat that bit as "not polled" and yield. The mechanism is sound but as written it starves the second station — §8A.
Starvation (why 8A is a blocker). dw1000.cpp:201 re-arms the timer on every foreign frame. Station A ranging at ~30 Hz puts a foreign frame on the air every ~11 ms at B's anchors; each one pushes B's deadline ≥10 ms further out, so B's backoff never expires (P(random ≤ 11 ms) ≈ 1%). B reports UWB_Backoff forever, never transmits, so A's anchors never hear B and A never yields. Whoever is already running wins permanently — in both directions, after any handover. A passive backoff can only hand the channel over if the waiting side is guaranteed to transmit after a bounded wait (classic CSMA). Fix: arm once per busy period, expire, transmit.
Bench result, firmware sC3.0.69 (2026-10-13, Fly PC id 1 + Mob PC id 11, tag 56).
  • 8B works: opcode 19 = 0 releases an armed backoff at once and the anchor ranges on the next request; re-enabling does not re-arm by itself.
  • Arming works: five rounds of the other station's traffic arm all three anchors.
  • Expiry is broken — blocker: the Status backoff field (now ms left) counts down and stops at 1; the anchor answers every SEARCH_TWR with bit 4 for good (watched 3 s, and indefinitely in earlier runs). One burst of foreign traffic silences a station permanently. Likely an off-by-one in the countdown or in the expiry compare (< vs <=, or a decrement that stops at 1).
  • 8C half done: Status carries ms left; the TWR reply's distance field is still 0 on a backed-off frame, so the PC cannot size its yield.
PC-side workaround in place: an anchor that reports backoff for longer than 250 ms (+0–150 ms jitter) is released with opcode 19 off/on and polled again. Measured, both stations on one tag for 20 s: 42 + 30 valid ranges/s (each alone: 81–89/s), p95 gap 83 / 229 ms; with backoff off: 13 + 10/s, p95 gap 431 / 368 ms, max 3.6 s. Field scenario (one station alone 10 s, the other joins for 20 s, the first stops), both orders: the newcomer's first range after 0.4–1.4 s; while both run 21–48 valid ranges/s each, worst gap 0.7–1.9 s; the station left alone is back to full rate (85–90/s) within the first second. Releasing a whole station at once instead of per anchor measured worse (worst gaps 5–6 s). With expiry fixed, the release becomes the rare §8A bounded wait instead of the normal path, and the fine window of 8D can interleave the stations per exchange, which is what will shorten those overlap gaps.
Bench result, firmware sC3.0.70 (2026-10-14, same rig). Expiry fixed: after a burst of the other station's traffic the Status field read 42–44 ms left, counted down to 0, and the anchor ranged again by +134 ms. TWR reply: carries the backoff bit only, by design (no time field; only Status counts down). That is all the PC needs: it polls every round anyway, so the next reply shows when the backoff has ended. Measured (both stations ranged lower alone than the day before, 60–68/s, so compare within the day): simultaneous start 30.6 + 31.5 valid ranges/s, p95 gap 111 / 90 ms (backoff off: 14.1 + 8.7/s); join/leave both orders — newcomer's first range 0.4–0.75 s, 27–45/s each while both run, worst gap 0.8–1.9 s, full rate again within 1 s. A 30 ms PC yield was tried and was worse (fewer whole rounds). The remaining overlap gaps are slot-like alternation; the fine window of 8D is the next firmware lever. (PC side since: taking turns, ON/OFF 250/250 — Mob's share 0.3–1.1 → 7.3–8.0 valid ranges/s with Mob ranging from its front anchor only.)

8A  blocker  Arm the backoff once per busy period; own-pc_id frames must not clear it — anc/src/dw1000.cpp:198–202 (dwScanMode)

/* current: every foreign frame re-arms (never expires under continuous foreign traffic);
   every OWN frame clears it (A's own next poll erases the yield B just earned) */
if (dwmInfo.detec_pc_id == true){
    dwmInfo.backoff_timer = 0;
}else{
    dwmInfo.backoff_timer = _1ms_tick + random() % TIME_TOP_RANGE_MS + MIN_BACKOFF_MS;
}

/* → arm ONLY when not already running; a running timer is left alone by both own and foreign frames.
   "Running" = deadline still in the future; an expired deadline counts as idle so it can re-arm on the next busy period. */
bool running = (dwmInfo.backoff_timer != 0) && (dwmInfo.backoff_timer > _1ms_tick);
if (!dwmInfo.detec_pc_id && !running) {
    dwmInfo.backoff_timer = _1ms_tick + random() % TIME_TOP_RANGE_MS + MIN_BACKOFF_MS;
}

Bounded wait: at most MIN_BACKOFF_MS + TIME_TOP_RANGE_MS − 1 after the first foreign frame, the next SEARCH_TWR goes out regardless (main.cpp:252 already clears the timer on expiry and ranges). That poll is what the other station's anchors hear, back off from, and report to their PC, which then yields. Without the own-pc_id change, an anchor that hears a sibling anchor's poll (same pc_id, every round) drops a foreign backoff in progress, so a running station never actually yields even once its PC wanted to. Collision risk on the barge-in poll is ~30% (air occupancy of one station ≈ 3×(3–4 ms) per 33 ms round); a collided poll is a normal miss and the next one goes out after the next backoff.

8B  blocker  BACKOFF_CTRL = 0 must also release an armed timer — anc/src/main.cpp:281–283 (UART_OPCODE_BACKOFF_CTRL)

/* current: disables the scan only — an already-armed deadline keeps blocking SEARCH_TWR (main.cpp:252) until it expires */
if(msg.op_backoff_ctrl_req.BackOFF_CTRL == 0){
    BackOFF_CTRL = false;
    dwmInfo.backoff_timer = 0;   // → release: "disable backoff" means "poll on the next SEARCH_TWR"

This is the PC's barge-in lever: after N consecutive UWB_Backoff replies the PC sends opcode 19 = 0 to one anchor, polls once (making the other station yield), and sends 19 = 1 again. With 8A in place barge-in is rarely needed; without 8A it is the only way for the second station to get in, and today it costs an extra ≤209 ms wait because the armed deadline survives the disable. One line.

8C below is dropped (2026-10-14): the PC uses only the backoff bit of the TWR reply and needs no time — it polls every round, so the next reply shows when the backoff ended. sC3.0.70 already clears the bit on expiry and counts down in Status. Kept for the record.

8D  choose  Backoff window: coarse (TDM-like, 300 ms slots) or fine (exchange-level interleave) — anc/inc/dw1000.h:93–94

ModeConstantsBehaviour with two stationsPC side
Coarse (today's values)TIME_TOP_RANGE_MS 200
MIN_BACKOFF_MS 10		 Stations alternate in bursts: one ranges at ~30 Hz until the other barges in (≤209 ms after it first hears it), then yields. Fine (recommended)TIME_TOP_RANGE_MS 15
MIN_BACKOFF_MS 1		 Backoff on the scale of one exchange (~3–4 ms air, ~11 ms with UART). Stations interleave per exchange; each gets ~12–15 Hz with jitter and no holes. No handover protocol, no starvation, no yield timer. Requires 8A (with re-arm, a short window makes starvation worse, not better). On bit4: re-send SEARCH_TWR to the same anchor after ~5 ms, up to 3 tries (a rejected request costs ~1 ms of UART), then move on.

The PC's position/bearing filters propagate with the measured dt (CV predict, dt-scaled gates), so either mode is safe for the filtering; the fine mode is better for it (jittered 15 Hz beats 30 Hz with 300 ms holes — fewer lost rounds, less lag at every handover). Both values are compile-time; a runtime setter (opcode 19 payload byte 2 = top-ms) would let the PC pick per deployment.

8E  important  Seed random() per anchor — anc/src/main.cpp init (before the main loop); promotes 5C

§9  Attributable CIR, per-exchange timing, negotiated TX power (host request, 2026-10-21)

Line numbers in this section reference the current anchor/tag source (Anchor/Core/Src/dw1000.cpp, Anchor/Core/Lora/Src/Lora.cpp, firmware anc3.1.5). Host side: hitan_rust on the same date.

Why. The field failure that matters is close range with no line of sight — a MOB station near the ground, the tag behind bushes or rocks. Both radios misbehave for one reason: a weak direct path and a strong reflected one. LoRa: the receiver sits near compression (above ≈−30 dBm), the level differences between anchors that carry the direction are squashed, and two-ray fading off the ground swings each level ±8 dB within seconds. UWB: the first path is weak against the reflections, the accumulator saturates on the strong path, and the latched diagnostics the host gates on stop describing the leading edge; bearings scatter 12–14° per round at 1 m (bench replay 2026-10-21). What the host can do is bounded by what the anchor reports. Today only dwt_readdiagnostics is latched per valid exchange (dw1000.cpp:355, dwRange); LDE_PPINDX and ACC_MEM are read live over opcode 12 after RX has re-armed, so they belong to whatever frame came next — the host withholds prNlos for that reason. Measured on the truth-labelled recordings (examples/nlos_features.rs): the three latched first-path taps carry no NLOS information (AUC 0.46); RX−FP is the only discriminator and it is weak (AUC 0.62–0.76).
Rule zero for everything in §9: the link is never lost. Losing communication with the tag is the one failure that is not allowed; every adaptive change below is built so that the worst case of a bad decision, a missed frame or a crash mid-negotiation is a few hundred milliseconds on the robust profile — never a tag that cannot be reached.
  • Control plane stays robust, always. The anchor→tag LoRa command path (wake-up, poll, profile and power requests) is fixed at maximum power and the robust spreading factor, and the tag's LoRa receiver stays on that configuration. Only the tag's beacon and the UWB exchange adapt. LoRa and UWB are separate radios on both sides, so the LoRa control channel is a permanent back door: any state can be undone from it.
  • Profile 0 is the ground state. Any doubt on either side → profile 0, unilaterally and at once. Tag: no frame from any anchor for 1 s. Anchor: two consecutive polls unanswered. Power-up, reset and watchdog restart land on profile 0. Wake-ups always go at profile 0.
  • Make-before-break. A move to a less robust profile or a lower power needs the tag's echo of the request and the anchor's confirmation of that echo (three frames) before either side switches, and two consecutive frames with the level inside the target band after the switch before the next step. A move to a more robust profile or higher power takes effect immediately and without confirmation.
  • Rate-limited and bounded. At most one step every 2 s away from robustness; no limit toward it. Power never below the level that leaves 10 dB of margin over the receiver's sensitivity at the current range, measured at the anchor, not predicted.
  • Channel changes are opt-in and proven first. Shipping builds keep UWB channel 4 disabled until the bench shows ≥ 80 % valid exchanges at 10 m with the installed antennas; even then the near profile falls back to channel 2 after one missed exchange.
  • Chaos test, before any of §9D/9H ships. 100 trials each of: walk the tag away at a run during a step down; cover the tag's antennas by hand; power-cycle one anchor mid-negotiation; power-cycle the tag; two stations on one tag. Pass criterion: the tag is reachable again within 1 s in every trial, zero cases of permanent loss. One failure blocks the release.
Host side, no firmware needed. (1) LDE NLOS preset: LDE_CFG1 is live-tunable via opcode 14 (dw1000.cpp:22, default 0x6D = LOS); APS006 Pt 2 recommends NTM 7 / PMULT 3 → 0x67 for NLOS — offered as a LOS/NLOS knob, not a default (more false first paths in clean air). (2) Level-dependent range bias (APS011): the received level is in the diagnostics, so the bias table is applied on the host.

9B  Latch a CIR window around the first path, new opcode 21 READ_CIR_WINDOW important

In the same latched block, 32 complex accumulator samples starting 8 before the detected first path, read while the accumulator still holds this reception (before RX re-arms):

9D  Negotiated TX power, tag and anchor (AGC-style) important

Goal: keep every receiver in its linear range at any distance — LoRa level differences stay meaningful close in, the UWB accumulator does not saturate. Start at today's maximum and step down only as the tag comes close; back to maximum the moment the tag goes quiet.

  • Loop on the anchor (not the host: it must react within a few packets, and must not depend on the UART). LoRa target: SignalRssiPkt at the anchor in −70 ± 6 dBm. UWB target: rx_power_dbm (from the diagnostics) in −80 ± 5 dBm — flat on the APS011 bias curve; above −65 dBm the DW1000 saturates.
  • Steps: one per packet; 2 dB for LoRa (SetTxParams, Lora.cpp:249, today fixed at TX_OUTPUT_POWER); one level for UWB from a table of 8 TX_POWER register values 3 dB apart, from the current maximum (dw1000.cpp:134) downward; smart TX power stays disabled. Dead band: no step inside the band.
  • Verification: the next frame from the tag carries the power it actually used (below); a mismatch for two frames resets the request to maximum.
  • Floor and fallback (rule zero): never request below −9 dBm LoRa or the lowest UWB table entry, and never below 10 dB of measured margin; after 1 s with no frame from the tag, request maximum again, and the tag returns to maximum by itself after 1 s without hearing an anchor; wake-up packets and all anchor→tag LoRa commands always go at maximum. A lost tag is found at full power first.
  • Three anchors, one tag: the tag obeys the most recent request; one station's anchors share one target so their requests agree within a step; the front anchor (the only UWB ranger on MOB) owns the UWB request.
  • Over the air: the anchor's UWB poll and LoRa wake/poll frames carry req_lora_tx_dbm (i8) and req_uwb_tx_level (u8); the tag's response frames carry the two it used. Older tags ignore the request and report 0x7F/0xFF, forwarded unchanged (9C), so the host can tell.
  • Host: switched and configured through opcode 22 SET_LINK_FEATURES (9I), applied by the station worker like the backoff toggle; the current request and the tag's echo in the STATUS reply. The host normalises the hot/cold bar and the LoRa calibration by the reported tag power (level + (max − reported)) so a quieter tag does not read as a farther one. Default off until the field test says otherwise.

9E  LoRa frequency diversity phase 2

Near the ground the level at one frequency sits in a fade for seconds. The tag alternates two channels by packet-counter parity, the anchors listen in step, the host averages direction across the pair. A bigger change (channel plan, per-channel duty cycle, both firmwares); only if 9D leaves the arc unstable near the ground.

9F  Repeat the exchange and report the minimum important

Anchor only, no negotiation. NLOS error is one-sided: a reflection only ever makes a range read long. On a SEARCH_TWR the anchor runs K exchanges back-to-back and reports the shortest valid range (and that exchange's diagnostics). K adapts to the anchor's own last diagnostics: 1 while RX−FP is under the soft threshold, 3 when it is above. Cost ≈11 ms per extra exchange; the station worker already tolerates longer rounds. Request byte: SEARCH_TWR payload gains an optional third byte k_max (0 = anchor decides, 1–5 = fixed); reply byte 24 k_used. Host use: none required — the range is just better; the host reads k_used for the round-time bookkeeping and the per-exchange tick (9C) of the reported exchange. The cheapest large NLOS win on this list.

9G  LDE preset per state important

Anchor only. The anchor switches LDE_CFG1 itself: NLOS multiplier (NTM 7 / PMULT 3, 0x67) while its last RX−FP sits above the soft threshold, LOS (0x6D) when it clears, with a dead band of 2 dB and a hold of 10 exchanges so it does not chatter. Requires the RX reset the driver notes after an LDE change (dw1000.cpp:234). The host keeps its opcode-14 override; a STATUS bit reports which preset is active. Pairs with 9F: when the anchor flips to the NLOS preset it also raises K.

9H  Link profile negotiation (one byte, not six parameters) important

Everything the tag must change in step with the anchor — TX power (9D), frequency diversity (9E), and the radio settings below — is negotiated as one profile index, with the request / echo / confirm / fall-back state machine of rule zero. The anchor picks the profile from RX level and range; the tag echoes it in every frame; both drop to profile 0 after 1 s of silence; wake-ups and all anchor→tag LoRa commands always go at profile 0. A profile only ever changes the tag's beacon and the UWB exchange, never the LoRa control path.

9J  Change handshake: the tag is told, acknowledges, and nothing switches until both sides have proof required

Every change the tag must apply — power, profile, channel alternation — goes through one three-way handshake with a sequence number. No side ever switches on a request alone, and no side is ever on a configuration the other does not know about.

StepFrameCarriesWho switches
1 requestanchor → tag, in the UWB poll and in the LoRa command frame (max power, robust SF)seq, requested profile, lora_dbm, uwb_levelnobody

  • Sequence numbers. One byte, incremented per request; a request with a stale or repeated seq is ignored by the tag; an ack for a seq the anchor did not send is ignored by the anchor. Every frame carries the sender's current settings, so either side can see a mismatch at any time.
  • Retries. The anchor repeats a request on every poll until acknowledged, up to 5 polls; then it cancels (the tag never switched, nothing to undo). The anchor repeats the confirm until the first frame arrives on the new settings, up to 5 polls; then both sides revert (next bullet).
  • Revert without a word. If the tag applied a confirm and then hears nothing on the new settings for 500 ms, it reverts to the previous settings on its own, and to profile 0 after 1 s total. The anchor, on 2 missed polls after a confirm, goes back to the previous settings for 2 polls and then to profile 0. Both reverts are unilateral and need no frame, because the failure case is exactly that no frame gets through.
  • Listen rotation (one radio per side). The DW1000 holds one configuration at a time, so during a transition the anchor alternates its receiver between the new and the old configuration poll by poll until proof arrives, and the tag, when idle, alternates between its current profile and profile 0 every 200 ms. A tag on any profile is therefore always reachable on profile 0 within 200 ms, and the LoRa command path reaches it at any time regardless.
  • Two radios, one truth. A request or confirm is valid if it arrives on either radio; the tag acknowledges on both. Losing one radio never stalls the handshake, and the LoRa path alone can always drive the tag back to profile 0 at maximum power.
  • Two stations, one tag. Requests carry the station's PC id; the tag follows the most recent confirmed request and tells both stations its current settings in every frame. A station whose requested settings are not what the tag reports simply adapts its receiver to what the tag reports (the tag's settings are authoritative), and does not fight: it never requests a less robust profile than the other station's last confirmed one.
  • Hard rule for the implementation: there is no code path on either side that changes a radio setting without a confirmed sequence number, except the reverts toward profile 0. A watchdog on each side asserts, once per second, that the configured radio matches the last confirmed state or profile 0; any other state is reset to profile 0.

9K  Two stations, one tag: adaptation is frozen, backoff untouched required

Backoff already costs performance today (§8: 42 + 30 valid ranges/s with two stations against 81–89/s alone, p95 gaps of 83 / 229 ms). Nothing in §9 may make that worse, and nothing in §9 may add a second mechanism that interacts with it. So the rule is not "coordinate the two", it is "do not adapt while there are two".
  • Two stations ⇒ ground state. While the tag has heard polls from more than one PC id in the last 2 s, it reports that, and every adaptive feature is off on both sides: profile 0, maximum power, K = 1, no requests sent, no handshake in flight. A station whose anchors have backoff armed, or that reads "two stations" from the tag, likewise sends nothing but profile 0. The §8 backoff, yields, duty cycle and release logic then run exactly as they do now, on the configuration they were tuned on.
  • Entering coexistence. If a second station appears while the tag is on a near profile at low power, the tag reverts to profile 0 at maximum power by itself (rule zero's unilateral revert, within one listen-rotation period) and the first station follows the tag's reported settings. The newcomer always polls on profile 0 and so reaches the tag within 200 ms; it never has to know what the tag was doing before.
  • Leaving coexistence. Adaptation may resume only after the tag has reported a single station for 2 s and no anchor of that station has backoff armed. The first step away from profile 0 is then one ordinary 9J handshake.
  • Anchor-local features that do not touch the air — 9G LDE preset, the 9A/9C reply bytes, the 9B CIR latch — stay on with two stations. 9F repeats do touch the air and are forced to K = 1.
  • The fixed duty cycle stays as tuned. While sharing the tag the host takes turns on fixed ON/OFF slots and releases a backed-off anchor after ON + 250 ms (§8, host side). Those timings assume one exchange per poll on profile 0; the freeze keeps that true, so the slots, the release margin and the yield are not recomputed for §9 and never need to be. The tag's silence timers (500 ms revert to the previous settings, 1 s to profile 0) must be longer than the longest configurable OFF slot plus the release margin, so a station's own pause can never look like a lost link to the tag; with two stations the tag is on profile 0 anyway, and a lone station never pauses, so duty cycling and adaptation never run at the same time. The only overlap is the hand-over, and it passes through the ground state.
  • Per-station sequence numbers (9J) remain, so a stale request from a station that has just gone quiet cannot be mistaken for a live one.
  • Regression gate. Every §9 feature ships only if the §8 two-station bench (both orders of joining, 20 s overlap, one station alone 10 s before and after) shows valid ranges per second and p95 gaps no worse than the sC3.0.70 figures, with the feature enabled on both stations. A feature that costs two-station throughput is kept off until it is fixed, whatever it buys alone.

Bench acceptance: Fly alone at 100 m on profile 0, Mob joins at 2 m: Mob ranges within 1 s on profile 0; the tag reports two stations; neither station sends a request; the §8 rates hold. Mob alone for 2 s after Fly stops: the first handshake to the near profile completes; Fly returns: the tag is back on profile 0 at maximum within one rotation period and Fly ranges within 1 s. 20/20 in each direction.

Only then does the anchor send the 17-byte extended poll {seq, req_lora_dbm i8 (0x7F = none), req_uwb_level, confirm_seq, profile_req} and the tag answer the 24-byte extended response {ack_seq, lora_dbm i8 (0x7F = no LoRa), uwb_level, profile_used}, flags in byte 9 (1 no LoRa, 2 quieter request pending, 4 two stations). Two unanswered extended polls, a legacy answer, 1 s of silence or another tag id → legacy polls for 5 s. A legacy poll always puts a new tag at maximum. Any old/new mix ranges exactly as before.
  • 9D UWB is per exchange and per anchor: the tag sends each response at the level that poll asked for and returns to maximum right after, so there is no shared state to get out of step. Louder at once; quieter one 3 dB level after 2 good responses and step_interval; one miss → previous level, two → maximum. Boards with the 10 dB maximum (HW ≠ 2) only have levels 0–3; the tag answers at its quietest and the anchor takes that as the floor.
  • 9D/9J LoRa has one owner anchor per station (opcode 22 byte 9 lora_owner, new): quieter steps go request (seq) → ack → confirm → proof, 5 tries each; louder at once; SNR < −7 dB (SF12 decodes to −20 dB; 10 dB margin after one more step; near compression the SX1262 reports only 3–4 dB SNR) or signal more than 3 bands under target → maximum at once; no packet for 1.5 s → maximum. Floor −9 dBm. The tag drops a quieter step after 500 ms and everything after 1 s without the owner; requests from other anchors only count when louder. The SX126x driver no longer forces 22 dBm in SetTxParams (clamps −9…22). The tag also acks in the UWB response only, not the LoRa beacon (its 6-byte format is fixed).
  • 9F: a miss ends the round; K = 1 with 9K. 9G: RX−FP soft threshold 6 dB (APS006), LOS preset = the opcode-14 value. Both act only above −90 dBm rx level: near sensitivity (the km range) RX−FP is high from noise, the NLOS threshold and "keep the shortest of K" would select noise-triggered early paths and read short; weak ⇒ LOS preset and auto K = 1 (a host-pinned k_max still applies).
  • 9I opcode 22 payload bytes 0–8 as tabled plus byte 9 lora_owner; a shorter payload sets the leading fields; empty = read; the reply is the 10-byte configuration. Bit6 off ⇒ DIAGNOSTIC_STATUS, SEARCH_TWR and STATUS keep their anc3.1.5 lengths. Bit6 on: DIAG 55 bytes; TWR 27 bytes (17–20 tick, 21 tag LoRa dBm, 22 tag UWB level, 23 SignalRssiPkt dBm, 24 k_used, 25 profile_used, 0xFF = unknown); STATUS gains the link_state block after the fault counters (payload 66–75: features, flags [1 extended frames, 2 LoRa owner, 4 handshake in flight, 8 reverting, 16 two stations/backoff], profile req, profile echo, req LoRa dBm, req UWB level, tag LoRa dBm, tag UWB level, LDE preset, k_used). Host: unpack_status_reply's len == 67 long-form test must become >= 67. Opcode 21 reply: 136 bytes with the checksum, n = 0 when 9B is off or before the first range.
  • Bench 2026-10-22 (FLY 4 anchors, MOB 3 anchors, tag3.2.0 HW 1). Features off: same rates as anc3.1.5/sC3.0.70 on the same script; every old/new pairing ranges. LoRa loop: 4.4 m behind a wall 22 → 0 dBm, SignalRssi −50 → −66 dBm; MOB at 1.1 m from −26 dBm (compressed) to −8 dBm tag power, −48/−46/−44 dBm at the three anchors — out of compression, spread kept, but −70 is unreachable at 1 m (the SX1262 floor is −9 dBm). Tag back at maximum ≈1.5 s after the host stops. 9F/9G behind the wall: K=3 + NLOS preset p10–p90 4.20–4.35 m, max 4.44 against 4.25–4.46, max 5.05 at K=1; +10 ms per extra exchange. Two stations: both freeze, rates unchanged against features off.
  • 9D UWB has no usable close-range metric. rx_power_dbm reads −78 dBm at 1.2 m line of sight and −77 dBm at 4.4 m behind a wall: the DW1000 estimate goes flat above ≈−85 dBm true power (UM 4.7.2), and the AGC keeps the CIR peak at 17–19k counts at both. So the UWB loop never steps down; it fails safe (maximum, as today) but buys nothing. Needs a different input — e.g. a level schedule from the anchor's own range, calibrated against the APS011 bias at known distances — before 9D-UWB is worth enabling.
  • 9K: the tag tracks the PC ids of polls addressed to it (2 s); the anchor also counts its own backoff arming. Either → legacy polls (same 12-byte airtime the §8 timings were tuned on), maximum, K = 1, no requests, until 2 s without a sign of a second station.
Bench acceptance.
  • 9A: the DIAGNOSTIC_STATUS reply grows by 8 bytes; prNlos per round near 0 in clean air, toward 1 with a metal box in the path.
  • 9B: the 32-sample window shows the first-path edge within its first 10 samples in clean air; nlos_features.rs extended with the window features scores clearly above RX−FP on the same recordings.
  • 9C: the three anchors' exchange_tick_ms sit 10–12 ms apart as the worker polls them; lora_signal_rssi ≥ lora_rssi − noise floor.
  • 9F: tag 3 m behind a metal box: the reported range's median error drops by at least half against K=1 on the same setup; round time grows by no more than 25 ms at K=3.
  • 9G: the STATUS preset bit follows a hand placed over the tag within 10 exchanges and clears within 10 after; no chatter at a steady 7 dB.
  • 9H: walking a tag from 50 m to 1 m, the echoed profile steps 0 → 1 → 2 with no missed round at the switch; pulling the tag away, both sides are back on profile 0 within 1 s of the first missed frame; ch 4 only if the bench shows ≥ 80 % valid exchanges at 10 m.
  • 9J: with the LoRa radio of the tag disabled on the bench, a profile change still completes over UWB alone, and the reverse; with frames dropped at random (20 %) the tag never ends up on a configuration the anchor is not listening on (the STATUS link block and the tag's own report always agree within 1 s); 100/100.
  • 9I: with every feature off the anchor's replies, round time and the tag's power are byte-identical to anc3.1.5 (replay compare); REVERT ALL from the tablet lands the tag on profile 0 at maximum within 3 frames, from any state, 20/20 trials.
  • 9D: tag 1 m from a MOB station: SignalRssiPkt settles in −70 ± 6 dBm within 3 s and the Configuration tab's LoRa spread stops reading "compressed"; UWB rx_power_dbm settles in −80 ± 5 dBm and the raw bearing scatter at 1 m drops from 12–14° to under 8°. Tag pulled to 50 m: both back at maximum within 1 s of the first missed frame.

§6  Bench verification & at-a-glance

Confirm §3 (RX deafness) in 5 minutes, before changing anything else. After dwConfig() runs, read GPIO_MODE (0x26:00) bits 19:18 (MSGP6): if they read 00 despite dwt_setlnapamode writing 01, the GPIO write silently failed — that is the smoking gun. Also read PMSC_CTRL0 bits 16/17 (expect 0/0 now, 1/1 after 3A). Scope GPIO6/pin 30 during RX (flat-low now → pulses high after 3A). Then apply 3A and re-run Skylab TX → Rev-D RX at 400 m. If loss drops toward 0–4%, confirmed firmware-fixable; if not, the deficit is in Rev-D's passive RX front-end (hardware).

Verdict on the TWR logic: sound. The directional A/B result (Rev-D→Skylab works, Skylab→Rev-D fails) is itself proof that the SS-TWR exchange, addressing, and timing are correct — a logic defect would be symmetric. The accuracy items (1A, 4B) affect distance values, not whether frames are received; the genuine logic nits (5B, 5C) don't cause the long-range loss. The long-range loss is a Rev-D receive problem — §3.
