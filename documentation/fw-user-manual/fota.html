Updating over the air

FOTA over UWB

How a board is updated through the radio, what protects the running firmware, and what the LEDs show.

What FOTA is

FOTA (firmware over the air) replaces the application of a board through UWB, without a cable on that board. One board is plugged into the PC and acts as the loader (the code calls it the flasher); the board being updated is the target. Any anchor or tag can be a loader and any board that runs 3.1.0 or newer can be a target. The protocol, the loader logic and the target logic are in Anchor/Core/Src/fota.c and Anchor/Core/Inc/fota.h; the Tag project carries identical copies, and board specifics (id, LEDs, battery, restoring the UWB settings) are in each project's fota_port.cpp.

Procedure

The wizard (PC tools) does these steps for you. An update of about 120 KB takes roughly 12 seconds: a 5 second countdown, under 1 second of data at 6.8 Mbps, then the target writes flash, reboots and the loader checks it.

  1. Load. The PC enters FOTA loader mode and copies the image into the loader's RAM in chunks of up to 128 bytes. The image is checked first: it must be at most 512 KB, its vector table must point into the application region, and its compiled-in version string must match the target kind.
  2. Handshake. The loader sends HELLO at the normal UWB setting that every board listens on. The target answers HELLO_ACK with its kind, hardware revision, battery, version and current application CRC, and starts a 5 second countdown. A target that does not answer is reported as "no target answered".
  3. Transfer. After the countdown both boards switch to the data rate: 6.8 Mbps first, then 850 kbps and 110 kbps if the link drops. Every chunk is acknowledged with the next offset; unacknowledged chunks are resent.
  4. Commit. The loader sends the size and CRC. The target checks the CRC of the image in RAM, writes bank 2 and the header page from RAM, reads the flash back and rewrites it (up to three times) if anything differs, then resets.
  5. Verify. The bootloader checks the CRC again at boot. The loader queries the rebooted target at the normal setting and reports Update OK only if the reported CRC equals the image CRC.

What protects the target

  • The target stores the image in RAM and writes flash only after the whole image has arrived and its CRC matches.
  • If the radio link drops, the target gives up after 6 seconds and carries on with its old firmware. Retry.
  • A target or loader with a battery gauge refuses to start below 30 %. Tags always have a gauge; an anchor reports one if a battery pack is wired to it. Boards with no gauge (USB powered anchors) report 255 ("no gauge") and are always allowed.
  • The image kind must match the board: an anchor image for a tag is refused ("wrong device kind").
The one case FOTA cannot recover. Losing power during the few seconds of the flash write leaves the board in its bootloader. Flash it over USB (htn_fw.py flash) or with an ST-Link.

A tag stays awake while it counts down as a target. Sleeping tags are not reached by UWB: wake them first (htn_fw.py wake) or update them while they are on USB or ranging.

Data rates

The handshake always uses the normal 110 kbps setting. The data phase starts at 6.8 Mbps (fast, a few metres) and, if the link drops, retries at 850 kbps and then at 110 kbps (slow, long range). The wizard's Data rate box and the --rate option can start lower. After an update, or when a session is aborted, both boards return to the normal ranging settings; the fast settings exist only during a transfer.

LEDs

Two LEDs per board show FOTA. On a tag: the status LED and the link-up LED. On an anchor (rev D has no status or link LEDs): battery-bar LED 0 (PE14) as status and battery-bar LED 3 (PF15) as link.

Power

The target must be powered. Rev D anchors run from USB power only (a charger or power bank is enough, no data connection needed); their battery input does not supply the board. Tags run from their battery.
