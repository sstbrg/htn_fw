Procedures

Build and flash

Build the three projects from the command line, flash with an ST-Link or over USB, and keep the bootloader safe.

Toolchain

The firmware builds with arm-none-eabi-gcc. CI uses Ubuntu 24.04's GCC 13.2 and local builds are tested with the same toolchain.

sudo apt install gcc-arm-none-eabi libnewlib-arm-none-eabi libstdc++-arm-none-eabi-newlib

For ST-Link flashing install stlink-tools 1.8.0 or newer. The Ubuntu OpenOCD 0.12.0 has no flash driver for the U5A5 (device id 0x481) and cannot be used. STM32CubeProgrammer is the full-support fallback (option bytes, TrustZone).

Building

tools/build.sh Anchor
tools/build.sh Tag
tools/build.sh bootloader_hitan
tools/build.sh Tag clean          # extra arguments go to make

The script regenerates Debug/objects.list from the makefile's object list, so new source files are linked without the IDE, then runs make -C <Project>/Debug all with one job per CPU. The generated Debug makefiles are tracked in git; the build products (.o, .elf, .hex, .bin, .map, .list, objects.list) are ignored.

You can also build inside STM32CubeIDE. Each project contains its .ioc file; regenerating code from CubeMX keeps the code inside the USER CODE BEGIN/END markers.

Versioning

Every image handed to anyone gets its own version. The version is the VERSION define in <Project>/Core/Inc/main.h, together with a one-paragraph history entry in the comment above it. Bump it with PY tools/htn_fota/fw_release.py bump anchor|tag [--part patch|minor|major | --set X.Y.Z] [--note "..."]. The version string is compiled into the image; the PC tools find it by pattern to tell an anchor image from a tag image.

Flashing

There are three ways to get firmware onto a board. Pick by the state of the board.

SituationMethodNotes
Board runs HITAN firmware 3.1.0 or newer, target out of cable reachFOTA over UWBWizard or htn_fw.py fota. No cable on the target. See the FOTA page.
Board runs any HITAN firmware or sits in its bootloader, USB cable availableUART bootloaderhtn_fw.py flash <image.bin>. Works on any firmware version; used to bring the first FOTA-capable image onto a board and to update the FOTA loader itself.
Blank chip, bootloader missing or damaged, or board stuckST-Link (SWD)Needed once per board for the bootloader. Flash the .hex.

Over USB, through the bootloader

PY tools/htn_fota/htn_fw.py --port /dev/ttyUSB0 flash releases/tag/3.3.1/Tag.bin

The tool reads the image, checks the vector table, reads the board status, and if an application answers it asks for confirmation (-y skips it) and sends UPDATE_FW to enter the bootloader. It then erases bank 2 (START_PROG), writes the image in 128-byte chunks (WRITE_BUFFER), and sends HEADER_FILE with the CRC and length. The bootloader verifies the CRC and starts the application; the tool prints the new status.

With an ST-Link

Anchor/flash_anchor.sh probe       # ST-Link and target detected?
Anchor/flash_anchor.sh             # flash Debug/Anchor.hex with st-flash
Anchor/flash_anchor.sh reset       # connect under reset (needs NRST wired)
Anchor/flash_anchor.sh cubeprog    # fallback through STM32_Programmer_CLI

st-flash --format ihex write Tag/Debug/Tag.hex
st-flash --format ihex write bootloader_hitan/Debug/bootloader_hitan.hex

The hex file carries its addresses (application at 0x08200000, bootloader at 0x08000000), so flashing an application hex does not touch the bootloader.

Do not write a .bin with st-flash to 0x08000000 for an application. That overwrites the bootloader. Use the hex, or give the .bin the address 0x08200000 explicitly.
Flashing is the operator's decision. Confirm the target board and the image before every flash, especially when several boards are on the bench.

Serial port

Anchor and tag UARTs run at 921600 baud, 8N1. Never open a port at another baud. The firmware re-arms the receiver after a UART error since 3.1.5, but a framing error from a wrong baud on an older image leaves the board deaf until it is power cycled. USB cables are a common failure: on error -71 or a failed enumeration (visible with journalctl -k), replug the cable or use another one. Stable port names are under /dev/serial/by-id/. Your user must be in the dialout group.

Releases and CI

A release is a folder releases/<anchor|tag>/<version>/ holding the .bin, .hex, .elf, .map and a manifest.json with the version, bootloader CRC, size, sha256, git commit, toolchain and date. The releases/ folder is not in git. Official releases are built by CI on every merged pull request and published on GitHub as fw-anc<ver>-tag<ver> with one asset, htn-fw-anc<ver>-tag<ver>.zip. Download the zip and place it, or its unpacked contents, into releases/; the tools never contact GitHub themselves, and check each image's sha256 on import.

The workflow is .github/workflows/firmware.yml. On a pull request it builds both images, uploads them as an artifact, and runs fw_release.py ci-check-version, which fails when an image differs from the one already released under the same version. On a push to main it builds and publishes the release.
